# AGENTS.md: yavs-dap

Read the root `AGENTS.md` first. This file is for an agent about to change `crates/yavs-dap`.
The design is `docs/plan.md` (`yavs-dap`, M8) on the interpreter's debug hooks,
`docs/design/ir.md` 3.4.

## 1. Purpose and boundaries

- The Debug Adapter Protocol server behind `yavs run --dap=PORT|stdio`: builds the simulation
  with every process attached to one `yavs_interp::DebugSession`, runs it, and answers a DAP
  client: breakpoints, stepping, pause, stack, variables, evaluate, output, exit.
- Does not: elaborate or lower (the CLI hands it an `Elaborated` with IR), parse the command line,
  or drive the kernel other than through `SimControl` and the session (plan: nothing else drives
  simulation).
- Depends on: `yavs-diag`, `yavs-elab`, `yavs-interp`, `yavs-ir`, `yavs-kernel`, `yavs-sem`,
  `yavs-logic`, `yavs-std` (TIME literals, `value::literal` for values typed by the user),
  `yavs-syntax` (breakpoint conditions), `yavs-wave` (live waves), `serde_json`. Called by: `yavs` (`src/elab.rs`, `run`).

## 3. Design decisions that bind this module

| Decision | Why | Source |
|---|---|---|
| Processes run on one thread under `--dap` (`Config::threads = 1`, the CLI warns `W0109` for more) | A stop inside a process is mid-delta; one thread makes every stop a defined point and sessions identical at any `--threads` | ir.md 3.4, `docs/decisions.md` "DAP server" |
| DAP threads are processes: `threadId` = session process index + 1, shown as `design::Proc::label` (`Elaborated::proc_label`, the name in every text since #992): the dotted path, or for a process without a label what it is and where (`tb.clk <= ... (tb.vhd:17)`). Everything that is looked up keeps `proc_name` | One debuggable sequential thing per process; `_p0` says nothing to a user | The debugging list of `docs/plan.md`, #942 |
| Frame id `threadId << 16 \| depth` (outermost 0), variables reference `frameId << 2 \| scope` (0 hierarchy, 1 locals, 2 signals, 3 generics); references from `CHILD` (2^32) on index a table cleared at every stop (`Shared::nodes`): a composite's children (local or signal plus a field and element path, re-read on each request) or a hierarchy region | Scopes stay stateless (data breakpoint info decodes them on the reader thread); children need a path | this file |
| Composites expand: records by field (`namedVariables`), arrays by index with `indexedVariables`, so a client pages them (`start`, `count`); children are named by field or index value. An array whose whole value is one string (`literal_image`: a vector, a string) has no children: one bit is read as `v(3)`; only one cut short at 256 elements keeps them | VS Code chunks large arrays itself; the maintainer's session (#953) | issue #326, #953 |
| The Hierarchy scope (expensive) and `yavs/hierarchy` (reader thread, static: regions, process names, signals) show the elaborated regions without processes and component scopes; in the scope a process shows its state | One tree for the Variables view, one for clients that draw their own | issue #326 |
| Requests that need no stop (`initialize`, `launch`, `setBreakpoints`, `configurationDone`, `threads`, `pause`) are answered on the reader thread; the rest go to the simulation thread and are served only while stopped (`the simulation is running` otherwise) | The simulation thread is busy inside `SimControl::run_until` | this file |
| A line breakpoint is set on the outermost statements starting on the line, or the next line with any (`Design::line_stmts`); the response gives the actual line | Editors expect breakpoints to slide to code | this file |
| Pause sets both the session pause (a running process stops at its next statement) and the kernel `Interrupt` (between cycles); the kernel pause that follows a process stop is swallowed (`paused_in_process`), an untaken session pause cancelled (`DebugSession::cancel_pause`) | An endless loop inside a process must be pausable; one pause is one stop The `pause` response is sent before anything is paused, so the stop never reaches a client ahead of it (#441) | this file |
| `yavs/runFor`/`yavs/runUntil`/`yavs/stepDelta`/`yavs/stepTimestep` are `SimControl::run_until`/`step_delta`/`step_timestep` in the run loop (`Run`); from a stop inside a process they are queued (`Shared::queued`) and the kernel paused, so they start once the cycle has ended (a delta step is then that end) | Nothing but `SimControl` drives the kernel; a process stop is mid-cycle | issue #324 |
| A stop during a run to a time does not cancel it: the run loop keeps the limit until it is reached, so `continue` resumes it | One rule for line, signal and pause stops; matches a `run` command resumed after a breakpoint | this file |
| Custom run requests answer, then send `continued` (thread of the stop, or 1) | A client marks the session running only for the standard resume requests | VS Code |
| Signal breakpoints are one `SignalBreak` observer, subscribed before the run, whose shared watch list (`Watches`) holds every leaf of every signal breakpoint, on any change; `setDataBreakpoints` and `yavs/setSignalBreakpoints` each replace their own set (`Shared::sig_bps`), answered on the reader thread | The interpreter's signal breakpoint and the event bus, no second watcher; VS Code resends all data breakpoints on every change and must not drop the custom ones |
| Values the user types (value breakpoints, `yavs/force`, `yavs/deposit`, `setVariable`) go through `design::typed_literal`: `yavs_std::value::literal` for the target's type (scalars as `'VALUE` reads them, any unit of a physical type, string and bit string literals, aggregates), then the quotes a bit-like target leaves no doubt about; a failure names the target's type and what it takes. Compared or written as `Lit`; after a pause with hits, a change that matches no value breakpoint resumes the run | One value syntax, VHDL's, for every request; the Variables view writes values in it | issues #322, #323, #953 |
| Force, deposit and release act on a signal or a part of it (`split_part`: the longest prefix that names a signal; `select`: fields, integer indices, a last slice in the signal's direction) through `SimControl::force`/`deposit`/`release`, one call per kernel element of the part (`Sig::part`, `Fmt::part`; issue #364), so only that part changes; a deposit encodes the current value with the part replaced; a request at a stop only queues them (`Shared::ops`), the run loop makes them before it runs on, so they take effect in the next cycle. From a stop inside a process the kernel is paused after the current cycle, as for a queued run, and that pause is no stop | Nothing but `SimControl` drives the kernel, and a process stop is mid-cycle; one path for both kinds of stops | issue #323 |
| `setVariable` on a signal is a deposit (of only the field or element set); on a local it writes the variable at once (`FrameView::set_value`, the whole value, composites keep their bounds); generics are refused | The Variables view's "Set Value" does what a user expects of each | issue #323 |
| Signal variables carry `__vscodeVariableMenuContext: "signal"` | VS Code's context key for the extension's force, deposit and release menu entries | VS Code |
| Generics are names after signals: `Proc::generic_lits` and `Region::generic_lits` (`Design::generics_at`) hold scalar and character-array generics as `(LitType, Lit)`; `typed_literal` is the one reader of a value the user types and gives its errors in plain words | One place reads what a user types and one list of names serves every command | issues #970, #972 |
| One evaluator for conditions, `examine`, Watch and hover (`eval_var`, then `cond`): a part of a local or a signal is a name in `cond`, through an access value too; `unsigned` and `signed` compare with numbers as `numeric_std` does, by the signal's type name (a local's type name is not in the IR: its numeric reading is refused where signed and unsigned differ) | Issue #935 asked for one way of reading an expression; it replaced a second part walker in `examine` | issues #930, #935 |
| Access values and protected objects are `LitType::Handle`/`Lit::Handle` in the values shown (`ir_decode_shown`, never a constant to compute with); `FrameView::deref` reads what they designate at a stop, in the stopped process's heap; children are `Node::Value`, a value of that stop that is shown and not written. A protected method's `self` parameter is a typed local so its object's variables are found; Locals lists them instead of `self` | Lazy, so cyclic lists are no problem | issue #936 |
| A session that cannot start tells its client (`refuse_session`): `launch` fails with the rendered diagnostic (from `serve`, and from the CLI through `refuse` when elaboration failed before `serve`); `serve_on` only returns the error, as its caller is the client | VS Code shows nothing of an adapter's standard error | issue #934 |
| `completions` is answered at a stop by `console::completions`, which also serves the terminal's Tab over the pipe; what follows a command comes from one table, `TAKES`, and the first word offers commands only. For a client that is not the console, the first target of several is what they have in common, as an editor's list takes its first item on Tab | One list of what a console takes; a Tab never picks | maintainer, 2026-10-31, #953 |
| Breakpoint conditions are evaluated by the server (`cond.rs`) over the values it shows, not lowered to IR: names are the stopped frame's and process frame's locals, then signals seen from the process (for a data breakpoint set without a frame, from the signal's region) or by path; predefined operators only. A condition is checked when it is made (`make_cond`: parse, then `Cond::check_types` over `Typed`, the types of the signals the process sees, and its variables as values that fit any type; what depends on a value waits) for line and signal breakpoints, a client's and the console's, and `run until`; a condition that does not parse, uses something unsupported or does not check is `verified: false` with the message, and the names left for the stop come back as `unchecked`; an error while evaluating is a stop with reason `exception`. A line breakpoint with a condition is an unconditional interpreter breakpoint; a stop whose condition does not hold returns `Resume::Skip`, so a step under way goes on. Hit conditions count the hits where the condition held (line and data breakpoints) | A running program cannot take new IR functions; most conditions compare locals and signals with literals | issue #326 |
| Live waves (`yavs/waveSubscribe`/`yavs/waveUnsubscribe`, reader thread, any time) are a `yavs_wave::Recorder` built by `record_to` with the client's `Selection` into `waves::StreamSink`; the bus observer `Tap` forwards to it, and one subscribed after the start records every value from its first callback on. Batches (`yavs/waves`) hold completed time steps, values base64 of the recorder's value bytes, decoded by the hierarchy's `encoding` (user, 2026-10-19), sent at a step end after `flushMs` or 256 KiB and always before `stopped` (`serve_stop`), `exited` (`Recorder::finish`) and the unsubscribe response | Same hierarchy, selection and final value per time step as `--wave`; the compact encoding the removed GUI design proposed (#871) | issue #325 |
| Wave batches go through a bounded queue (`waves::Stream`) written by a sender thread and by `Shared::send` before every other message; a full queue merges the newest batch into the last (last change per value, `merged`) | The simulation never waits for a client; batches keep their order with the rest of the session, so transcripts are deterministic | issue #325 |
| `serve` takes `Arc<Db>`/`Arc<Elaborated>` (a subscription builds a recorder on the reader thread) and an `attach` callback: the CLI subscribes its `--wave` and `--vhpi` observers to the debug build and gets a `Finish` run before `exited`; its `Report` callback receives the final kernel statistics and interpreter runtime for `YAVS_COUNTERS` | One observer setup and counter report for `yavs run` with and without `--dap` | issues #325, #696 |
| From a stop between cycles, every step request is a global step (next statement of any process) | No process is current there | ir.md 3.4 |
| Reports and `OUTPUT` text are `output` events (stdout carries DAP in `stdio` mode), sent as they are made (`LiveOutput`, the kernel's `LiveSink`; the observer's `report` gets what is committed later); runtime errors an `output` event of category `stderr` | stdout is the protocol channel; a process that never suspends still says where it is | `docs/cli-contract.md` 5, #939 |
| Shared variables: `Design::shared` (from `Ir::var_slots` and `Elaborated::shared_vars`), found by `Design::named`; values at a stop by `shared_value` (`Built::vars`, `Built::objects`) and `deref`. At a process stop the mutex of the shared state is held by that process's own run when it `holds_shared`: read through the `FrameView` then, never `yavs_interp::shared_var`. Shown, not written. Scope `Shared Variables` is a per-stop `Node::SharedScope` | The scope encoding is full | #938, #959, `docs/decisions.md` |
| `restart` request: `supportsRestartRequest` only over TCP (`Link::attached`), at a stop like the console's `restart` (`Next::Restart`), while running on the reader thread; it then runs on (`Link::client_restart`) instead of stopping at time 0; a refusal is an `important` output event and a successful answer | A launch session restarts by a new launch, which analyzes the sources | #963, `docs/decisions.md` |
| Disconnect stops the run (`Interrupt::stop`), then `exited`, `terminated` and the disconnect response, in that order | Deterministic transcript | this file |
| Over TCP the server shuts down its write side after the last message and waits up to 2 s for the client to close before exiting | Exiting with the socket open resets the connection on Windows and the client loses the last messages | CI, Windows |
| `Shared` is one simulation; `Link` is what outlives it (connection, queue of requests, `Kept`, console state). `serve_on` loops over `one_run`; the reader thread takes the current `Shared` per request. `restart` and `reload` end a `one_run` with `Outcome::Again`: `terminating` and `discard` make the old simulation end silently (`Interrupt::stop`, also out of a process that never suspends) | `restart` needs no state reset in the kernel or the interpreter: a new build from the same `Elaborated`, the same path as the first | issue #904 |
| `help` of a client that says `supportsANSIStyling` is an output event, command names in bold, with an empty result (VS Code keeps its bold for output, not evaluate results; the terminal says so on a colour terminal only); else the result, plain | Checked in a headless VS Code | #953 |
| The commands of the console are one table, `COMMANDS` (`Command`: name, group, `Form`s with the section of the reference they belong to and what they need (a viewer, a wave file), meaning, alias): `help`, `help COMMAND`, Tab and the user guide read it. A new command or subcommand needs its row and a section in `docs/console-reference.rst` starting `.. console: NAME` (or `NAME SUB`) and ending `.. console-end` (the synopsis between them is generated); the test `cli_reference_console_reference_is_current` fails without it, and `YAVS_BLESS=1 cargo test -p yavs --bin yavs cli_reference` rewrites the generated parts. Examples in that page are run by `crates/yavs/tests/docs_debugger.rs` (`YAVS_BLESS=1` rewrites their output) | A command cannot be left out or described by a second list | #944, #955 |
| The console is a DAP client of this server (terminal side in `crates/yavs/src/console.rs`, over a pipe); all commands are in `console.rs` here. `launch` with `yavsConsole: true` adds: a stop at time 0 before the first cycle, staying at the end of the run, stop notices (`important`), the `yavs/prompt` event | No second run control; the terminal, `--do`, `source` and an editor's Debug Console share one parser | issue #904 |
| A waveform viewer is the `Viewer` trait (`Attached::viewer` from the caller's `attach`; `console::tell_viewer` at each stop, after the file sync and before `stopped`; `wave` commands; `yavs/showSource` for its go to declaration; `on_notice` for what happens to it, an `output` event of category `stderr`; `AddError` tells a name the file lacks from a viewer in trouble) | WCP stays in the binary, `crates/yavs/src/surfer.rs` | issue #876 |
| Paths in frames and breakpoints are `std::path::absolute` of the source path (lower-cased as a key on Windows) | No `\\?\` prefixes; clients differ in drive letter case | this file |

## 4. Invariants and pitfalls

- `Front::on_stop` runs on the simulation thread inside a process's statement; it must not call
  `SimControl`. It reads signals through `Stop::ctx` (`At::read`).
- `Shared::rx` is locked only by the simulation thread (configuration wait, stops, end of run).
- The transcript tests depend on message order: only send from the simulation thread while it
  runs, and keep reader-thread answers to requests a client sends while stopped or before start.
- A queued force or deposit is lost when the session ends before the next cycle (disconnect).
- The wave queue is written with `out` locked first, then the queue (`Shared::send`, the sender
  thread); never the other order. A subscription's recorder is locked inside `Shared::wave`.
- Under `--dap=stdio` the CLI first dup2s descriptor 1 onto stderr (`yavs_vhpi::divert_stdout`) and hands the server a private duplicate of the original stdout (`set_stdout`), so plugin and foreign-library prints cannot corrupt the framing (#389). Any new stdout write in the CLI goes to stderr in such a run.
- Codes owned: `E0700`-`E0799`/`W0700`-`W0799` (in use: `E0701` connection cannot be opened,
  `E0702` live waves failed, `E0703` the console hook).
