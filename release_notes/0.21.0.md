yavs 0.21.0 adds cycle mode, an EXPERIMENTAL compiled mode for long runs of synchronous designs, turns the test runner's token server on by default, and fixes wrong values from a design's own resolution function and standard-logic types, element ranges of constants and signals that read a variable later reassigned.

- **EXPERIMENTAL, cycle mode:** `yavs run --cycle` runs the clocked and combinational logic of a design as compiled code once per clock edge and keeps the testbench in the event simulation. Values are two-state by default (`--cycle-exact-meta` keeps the exact metavalue rules), `--cycle-strict` and `--cycle-report` say what runs cycle-based and why, and a new user guide page lists everything it changes. Its options and what it accepts may change in a later release.
- **Cycle mode in test suites:** the compiled region is kept in the compilation cache, so the test cases of a design compile it once, and `vunit-yavs` has the experimental sim option `yavs.cycle`.
- **Token server on by default:** `vunit-yavs` lends the CPUs no test uses to the running simulations, and keeps a test slot's CPU free for its next test.
- **Fixed, wrong results:** a resolution function, a `std_ulogic` type or a `std_logic_1164` package that a design declares itself is used instead of the library's, and a signal assigned a variable's value keeps it when the variable changes later in the same process run.
- **Fixed, values at elaboration:** bits and slices of elements of constant arrays use the element subtype's index range, and an `in` port actual whose slice bounds or alias read a signal follows that signal.
- **Fixed, designs that failed:** long chains of operators no longer crash, port-map conversion functions may read other signals, array mode views work in concurrent procedure calls and `process (all)`, and an alias of an out-of-range slice is an error when it is elaborated.
- **Fixed, a false warning:** the most negative value of an integer type `rem` or `mod` -1 no longer warns of an overflow.
- **Faster verification-library testbenches:** message passing, queues and AXI-stream components run faster, and testbenches that create verification components in constants elaborate faster from their third run.
- **Compilation cache:** a full cache no longer slows every new entry, and tests that start together store their analysis once.

# Features

- Cycle mode, experimental: `yavs run --cycle` runs the clocked and combinational RTL of a design as compiled code evaluated once per clock edge and leaves the testbench in the ordinary event simulation, an opt-in mode for long runs of synchronous designs. It trades detail for speed: values are two-state (a metavalue reaching the region reads as `0`; `--cycle-exact-meta` keeps the exact rules), the reports and assertions of cycle-based processes below the top-level unit are not produced (a warning at the start of the run names those of severity error and failure, which then no longer stop the run), and waves, coverage, VHPI and the debugger cannot be combined with it. A process it cannot take stays in the event simulation; `--cycle-strict` makes each such process an error that says why and how to fix it, and `--cycle-report[=FILE]` shows what would run cycle-based without simulating. With `--cycle-exact-meta` a register or variable without a start value shows the testbench `'U'` until its value no longer depends on it, as in the normal mode. Only the logic that a clock edge or a changed input reaches runs, and the compiled region is kept in the compilation cache, under a size limit of its own that `YAVS_CYCLE_CACHE_MIB` sets, so the other test cases of a design compile it once. The test runner package `vunit-yavs` has the sim option `yavs.cycle` (`"off"`, `"on"` or `"strict"`), settable per library, testbench, test or configuration. Its options, error codes and what it accepts may change in a later release. The new user guide page "Cycle mode" says when it pays, what runs cycle-based, how to read the report, and lists everything it changes.
- The test runner package `vunit-yavs` starts its token server by default, at any `-p`, with one slot for each CPU the run may use: every simulation runs with `--threads=auto` and takes the CPUs no test uses only while its threads gain, including those of test slots that ran out of tests near the end of a run. A test slot keeps its CPU for a second after its test ends, so its next test does not start on a full machine. `--yavs-no-jobserver` or `VUNIT_YAVS_JOBSERVER=off` turns it off.

# Bug fixes

- A compilation cache that has reached its entry limit no longer makes every new entry cost a scan of the whole directory: a run that stores many entries into a full cache is no longer slowed by repeated listings and stats of it. (#1161)
- A resolution function that a design declares itself and names `resolved` on `std_ulogic` is now called: before, the library's `std_logic` resolution replaced it and the signal got wrong values. (#1162)
- A type named `std_ulogic` or a package named `std_logic_1164` that a design declares itself is no longer taken for the library's: its own operators and clock-edge function run, and a waveform on a signal of such a type no longer stops the run with a false error. (#1163)
- A conversion function in a port map that reads other signals of the instantiating region (an impure function such as `b => f(x)` reading `y`) is no longer rejected at elaboration: the port follows its actual in the same delta, and the function sees the current values of the signals it reads. (#1166)
- Expressions with many thousands of operators in a row, such as long generated sums of signals or generics, chains of declared operators and long conditions, no longer crash the simulator with a stack overflow. (#1167)
- A bit or slice of an element of a constant array of vectors, read during elaboration (a signal's initial value, a port actual, a constant), now uses the element subtype's index range: an element given by a bit-string literal or a function result had been read by the literal's own range, which gave a wrong bit or the error "slice direction differs from its prefix".
- A bit or slice of an element of a constant whose array subtype constrains its elements itself (`arr_t(0 to 3)(7 downto 0)` of an array of unconstrained vectors, or a record subtype constraining a field), read during elaboration, now uses that element constraint's index range: it had been read by the literal's own range, which gave a wrong bit or the error "slice direction differs from its prefix".
- A concurrent procedure call or `process (all)` with a signal parameter of an array mode view (`view (v) of arr_t`) now elaborates and runs; it stopped with an internal error. Its sensitivity is the whole array.
- A signal assigned a variable's value keeps that value when the variable is assigned again later in the same process run and the signal may be assigned again after that (`s <= v; v := x; if c then s <= ...`): the signal had taken the variable's new value.
- A slice whose bounds read a signal, as the actual of an `in` port (`d => x(k + 1 downto k)`), now follows the signal: it had been taken once at the bounds of elaboration. A `wait until` on such a slice, and the equivalent process of such an actual, now also wait on the signals of its bounds and of an aggregate's choices.
- An expression as the actual of an `in` port that reads a signal through an alias (`b => resize(rf(3 to 7), 16)` with `alias rf is r.f0`) now follows that signal; a `wait until` reading a signal through an alias waits on it too. Both had not waited on the signal and kept their first value.
- An object alias whose name has an index or a slice bound outside the prefix's index range (`alias a : signed(0 to 18) is s(32 downto 14)` of a one-bit `s`) is now an error when the alias is elaborated, also when nothing reads its value; it had only been warned about at analysis and then run.
- Expressions that chain thousands of operators (`a & b & c & ...`, as generated test vectors and tables are often written) now analyse, elaborate and run: analysis had crashed with a stack overflow at about 4000 operators.
- The most negative value of an integer type `rem` or `mod` -1, which is 0, no longer gives a false warning that static arithmetic overflows; a debugger breakpoint condition computes it as 0 instead of reporting an overflow.

# Miscellaneous

- A call whose array result the memo of pure calls keeps now copies the result once, straight into the memo's own storage, so a run of calls that never repeat does less work per call.
- A call whose result the memo of pure calls keeps now reuses the memory of a result it dropped, so a run of calls that never repeat allocates less.
- A testbench whose constant declarations create verification components or loggers elaborates faster from its third run: the functions that elaboration optimised are kept in the compilation cache and not optimised again.
- Compiling and optimising a design costs a little less: the lookup tables of the optimiser and of lowering use a cheaper hash. Code and results are unchanged.
- Concurrent assertions of the form `assert not (rising_edge(clk) and ...)`, and `wait until` conditions that combine a clock edge with `std_logic_1164` gates or with a user-defined `"and"` of a `std_ulogic` and a `boolean` that is the plain boolean `and`, now wake their process only on that clock edge, as `wait until rising_edge(clk) and ...` already did. Results are unchanged; such testbenches and designs run fewer process activations.
- Elaboration of testbenches that create verification components and loggers in constant declarations does less work: a function that has to run against the package state no longer has its callees lowered a second time for nothing.
- Message passing of the verification library runs faster on every tier: the small procedures in front of the ones that wait (send, receive, get a message, notify) are inlined into their callers, while traces, call paths and timeouts stay those of the calls. Finding and making them now costs less.
- Optimising a process after its temporaries were placed in the frame costs a little less. Code and results are unchanged.
- Short tests that use the verification library's queues, message passing and AXI-stream components run faster while they are interpreted: the interpreter now runs the small storage accessors behind them inline, while compiled code keeps calling them.
- Tests of one testbench that start together no longer each write the same analysis image to the compilation cache: one of them stores it.
- Under `--tier=auto`, a later run of a testbench that uses the verification library's message passing or AXI-stream components no longer stays slow in the cache worlds where the first long run happened to leave cheap library subprograms interpreted.
